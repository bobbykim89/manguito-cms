# A field's label and its storage key are separate; the storage key is immutable

`ParsedField.name` is a **label** — the public name consumers and the admin panel see. `db_column.column_name` is the **storage key** — the Postgres column, fixed for the life of the data. The two fields already existed as distinct concepts before this stage, and `fieldTypeRegistry` sets `column_name` to `raw.name` for every field type today, so label and storage key are equal for every field a schema author has never renamed — divergence does not exist yet. What this stage changed is that the api package's **top-level** read and write paths no longer *assume* equality: the REST route handlers, filter parsing, relation resolution, the GraphQL value and filter paths, and the record handed to a programmatic resolver were each audited to use the correct one. The audit stopped at the top level at first; a following stage recursed the outbound projection through nested rows and closed a matching gap in `sort_by`, both recorded under Consequences below. Divergence itself arrives with schema versioning, which folds a rename chain into `column_name` while leaving the label free to change.

The api package converts at exactly two boundaries, both closed by a `FieldKeyMap`. One is built per content, taxonomy and paragraph type, once, at startup in `app.ts`, keyed by the full machine name (`content--x` / `taxonomy--x` / `paragraph--x`) — and it throws on construction if a field's label collides with another field's column, matching how the app already refuses to boot on a broken roles registry rather than silently producing an ambiguous mapping. Inbound: each admin write handler computes `storageBody = fieldKeys.toStorage(body)` once. Outbound: every REST read response — public and admin alike — is projected through `projectRow` (`projector.ts`) at the route boundary, exactly once per response; `projectRow` maps the top-level row through `fieldKeys.toLabels(row)` first and then recurses into nested rows, described under Consequences below.

GraphQL never calls `toLabels` on a row and does not need to: each field resolves individually, and scalar fields go through `resolveFieldValue`, which reads the storage column while the GraphQL field name comes from the label. Relation fields resolve through `relationFieldResolver` and its dataloaders, which key off the FK column directly; system fields resolve inline. The one row GraphQL does project is the record handed to a programmatic resolver, because `ctx.get()` takes the schema field name. On both surfaces that projection runs *after* relation resolution and *before* the programmatic resolver, so a resolver reading `ctx.get('title')` sees the label the schema declares.

Only column-backed fields participate. Paragraph fields have no column (their association lives on the paragraph table via `parent_field`) and many-to-many references have none either (the junction table, whose name embeds the field name, owns the association). Both keep the label as their identity, so **renaming a paragraph or many-to-many field is not supported** — schema versioning rejects such a rename and directs the author to retire the older version first.

## Considered Options

- **Keep label and column identical; rename the column on a schema rename** — rejected: `drizzle-kit generate` cannot infer a rename from a schema diff and prompts interactively to distinguish rename from drop-plus-add. That is unusable in a non-interactive `manguito build`, and the drop-plus-add branch destroys exactly the data an older API version still serves.
- **A general `storage_key` on every field kind**, including paragraph and many-to-many — rejected for now: it requires changing `parent_field` semantics and junction table naming, both of which are persisted in existing databases. The narrower rule buys renameability for the fields authors actually rename.

## Consequences

- Relation resolution deletes the raw FK key from a row when it resolves into a different label; when they match it overwrites in place, as before. Applied identically to the `reference` and `media` branches in `relations.ts`.
- Filters are validated against labels and emitted as storage keys: both `parseFilters` (REST, `routes/query-params.ts`) and `translateFilters` (GraphQL, `graphql/filters.ts`) gained an optional `columnFor` mapper, so existing two-argument callers are unchanged and a client naming a raw column still gets the existing 400.
- GraphQL field *names* still come from labels (`naming.ts` is untouched); only value lookup, filter emission and sort emission changed. `fieldKeyMaps` is threaded `app.ts` → `createGraphQLHandler` → `buildGraphQLSchema` → resolvers, and the module stays behind its dynamic import ([ADR api/0006](./0006-subpath-exports.md)).
- Public route paths are now built in one module, `paths.ts`, which also makes the previously non-functional `api.prefix` option actually route. Both prefix-default sites — `app.ts` and `createAPIAdapter` in `index.ts` — normalize through the same `normalizePrefix`.
- Because Hono infers path-param types from *literal* path strings, computing paths through `paths.ts` erases that inference: three handlers (`routes/media.ts`'s media-item route, `routes/content.ts`'s item and taxonomy-item routes) carry a documented non-null assertion on `c.req.param(...)`, each guaranteed safe by the route pattern that registered it — the builder unconditionally appends the `:slug`/`:id` segment. A coming runtime version segment makes literal paths impossible anyway, so this is a permanent shape rather than a temporary wart.
- **Projection now recurses.** `projector.ts` walks every response row: the top level through `FieldKeyMap.toLabels`, as before, then paragraph children, resolved reference targets and junction targets, each through its own type's map — applied at exactly the boundary that already called `toLabels` once, so no resolver changed. GraphQL needed nothing here: `buildObjectType` already resolves each nested field by its own column.
- **No depth counter, because nothing can recurse forever.** `?include=` takes no nested `include` paths of its own, so a resolved relation cannot itself request another; paragraph nesting is capped at one level ([core 0005](../core/0005-paragraph-nesting-one-level.md)); and the walk stops at anything that is not a plain object — a bare uuid string, an array of them, or a `Date` — via an `isPlainRow` guard, so a relation left as a bare id (not `?include=`d) or a timestamp column passes through untouched. A reference cycle has nowhere to loop.
- **Nothing is mutated in place.** The relation cache in `relations.ts` keys resolved targets by `table:id`, so two parent rows can hold the very same nested object; `toLabels` already returns a fresh object per call, and the walk assigns that result rather than editing the source, so projecting one parent's copy cannot blank out another's.
- **Media is excluded from projection.** The `media` table has fixed system columns and no schema fields to map, so a media relation is left exactly as `SELECT *` produced it — there is nothing for a field key map to do with it.
- **Paragraph types now have field key maps too, in the same object as the other two.** `app.ts` builds one `fieldKeyMaps` covering content, taxonomy and paragraph types, keyed by machine name, and both consumers index it over that whole key space: `buildProjectors` walks `registry.paragraph_types` to project paragraph children, and `graphql/schema.ts`'s `buildObjectType` runs over paragraph types too. An earlier draft kept the paragraph maps in a sidecar object on the grounds that a paragraph type resolving to `undefined` inside `buildObjectType` was pinned behavior; nothing pinned it, and the separation preserved a real gap — a **programmatic field on a paragraph type** got no map, its projection to labels degraded to identity, and the resolver's `ctx.get('title')` read a storage-keyed record. Since the programmatic record is the one row GraphQL projects, that contradicted the rule directly. Every other GraphQL field resolves per field by column and is indifferent to this map, so widening it changes nothing else. What did change more broadly: `createFieldKeyMap`'s collision guard now runs against paragraph types too — a new reason a server can refuse to boot.
- **`sort_by` is now a split guard.** The route validates the incoming label against `SORTABLE_FIELDS` and maps it to a column with `columnFor`; the repository takes an optional `sortableColumns` set of columns and validates again before `quoteIdent` runs — a repository built without the option still validates against `SORTABLE_FIELDS` exactly as before, so the new guard is additive. Its rejection message deliberately does not enumerate the allowed set: under divergence that set holds storage columns, which must never reach a client envelope, and the routes name the valid *labels* instead. GraphQL's `sortBy` enum needed the same split guard and was easy to miss — two of its three internal values (`created_at`, `updated_at`) really are system columns, but `title` is a *label*, so the enum's value was reaching `ORDER BY` unmapped. `collectionResolver` now runs it through the type's `columnFor` (a system column has no label entry and falls through), and `app.ts` gives the GraphQL repos the same `sortableColumns` set every other repo gets. Its old rationale does not hold: "only indexed system fields are sortable" is false on both halves — `packages/db/src/codegen/` generates no indexes at all, and `title` is not one of the six `CONTENT_SYSTEM_FIELDS` (`id, slug, base_path_id, published, created_at, updated_at`). Sorting by a label a type lacks still reaches Postgres and 500s, left alone deliberately: schema-driven sorting is an agreed destination on its own timeline, not a blocker here.
- The programmatic resolver context is a **public extension API**: `docs/programmatic-fields.md` documents `ctx.get(fieldName)` as the stored value of a sibling field, and every example passes a schema field name. So the row it is given is projected to labels first, on both surfaces. REST does this by mapping before the resolver rather than after — programmatic fields are not column-backed, so their output keys are labels already and mapping afterwards was a no-op on them, which keeps it at exactly one mapping per response.
- Relation resolution is idempotent. Because it consumes the raw FK (and deletes the FK key outright when the label diverges), a second pass over the same row object would otherwise null out what the first pass resolved — and the same object does recur, since reference/junction targets are cached by `table:id` and the GraphQL dataloaders do not memoize by parent identity. `resolveRelationField` dedupes its batch by object identity and skips rows that already hold a resolved value.
- One existing test was changed rather than only added to: `packages/api/src/__tests__/relations.read.integration.test.ts`'s bare-reference-id assertion now expects the label instead of the raw column, because its fixture hand-writes a reference field whose label diverges from its column — a divergence no parser-produced schema can reach today — and the old assertion characterized exactly the column-name leak this stage exists to close.
